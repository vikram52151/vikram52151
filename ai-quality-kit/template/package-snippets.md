# npm / Angular snippets

Copy what you need into your frontend project. They make `npm run lint`, `npm run test:ci` and
`npm run build` (which the Stop hook and CI run) fail when lint rules, coverage thresholds or bundle
budgets are broken.

Versions: ESLint 9 (flat config), typescript-eslint 8, angular-eslint 19/20, Lighthouse CI 0.14,
Stryker 8 were current in 2025. **Check the latest versions** (`npm view <package> version`) before
installing, and install only with your package manager so the lockfile is updated properly.

## 1. package.json scripts

The gate looks for `lint`, `test:ci` (falls back to `test`) and `build`. Pick the `test:ci` line for
your test runner.

```json
{
  "scripts": {
    "start": "ng serve",
    "lint": "ng lint",
    "test": "ng test",
    "test:ci": "ng test --watch=false --browsers=ChromeHeadless --code-coverage",
    "build": "ng build",
    "mutation": "stryker run --incremental"
  }
}
```

- Karma (Angular up to v20 by default): `"test:ci": "ng test --watch=false --browsers=ChromeHeadless --code-coverage"`
- Vitest via the Angular CLI (default for new projects from Angular 21): `"test:ci": "ng test --watch=false --coverage"`
- Plain Vitest: `"test:ci": "vitest run --coverage"`
- Jest: `"test:ci": "jest --ci --coverage"`

`ng build` uses the production configuration by default, which is where budgets are enforced.

## 2. ESLint (flat config, Angular)

Install with `ng add angular-eslint` (it creates `eslint.config.js` and the `lint` target), then add
the stricter rules below. Generated by angular-eslint; the exact helper names change between majors,
so compare with what `ng add` generated.

```js
// eslint.config.js
// @ts-check
const eslint = require("@eslint/js");
const tseslint = require("typescript-eslint");
const angular = require("angular-eslint");

module.exports = tseslint.config(
  {
    files: ["**/*.ts"],
    extends: [
      eslint.configs.recommended,
      ...tseslint.configs.recommended,
      ...tseslint.configs.stylistic,
      ...angular.configs.tsRecommended,
    ],
    processor: angular.processInlineTemplates,
    rules: {
      "@typescript-eslint/no-explicit-any": "error",
      "@typescript-eslint/no-unused-vars": ["error", { argsIgnorePattern: "^_" }],
      "no-console": ["error", { allow: ["warn", "error"] }],
      eqeqeq: ["error", "always"],
      complexity: ["warn", 10],
      "max-depth": ["warn", 4],
      "no-restricted-imports": [
        "error",
        { paths: [{ name: "lodash", message: "Import single functions (lodash-es/<fn>) to keep bundles small." }] },
      ],
    },
  },
  {
    files: ["**/*.html"],
    extends: [...angular.configs.templateRecommended, ...angular.configs.templateAccessibility],
    rules: {},
  },
);
```

Also set `"strict": true` in `tsconfig.json` and `"strictTemplates": true` under `angularCompilerOptions`.

## 3. Coverage thresholds

### Karma (`karma.conf.js`)

`ng test --code-coverage` fails when coverage is below `check`. Generate the file with
`ng generate config karma` if your project does not have one.

```js
// karma.conf.js (only the coverage part shown; keep the rest of the generated file)
module.exports = function (config) {
  config.set({
    coverageReporter: {
      dir: require("path").join(__dirname, "./coverage"),
      subdir: ".",
      reporters: [{ type: "html" }, { type: "text-summary" }, { type: "lcovonly" }],
      check: {
        global: { statements: 80, branches: 70, functions: 80, lines: 80 },
      },
    },
  });
};
```

### Vitest (`vitest.config.ts`)

With Angular 21+ and the CLI's Vitest runner, check the Angular unit-testing guide for how your version
passes a Vitest config file or coverage thresholds to the `unit-test` builder.

```ts
// vitest.config.ts
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: {
    coverage: {
      provider: "v8",
      reporter: ["text-summary", "html", "lcov"],
      thresholds: { statements: 80, branches: 70, functions: 80, lines: 80 },
      exclude: ["**/*.spec.ts", "src/main.ts", "src/environments/**"],
    },
  },
});
```

### Jest (`jest.config.js`)

```js
module.exports = {
  collectCoverage: true,
  coverageThreshold: {
    global: { statements: 80, branches: 70, functions: 80, lines: 80 },
  },
};
```

These are whole-project numbers. Start at roughly your current coverage and raise them over time. For
"80% of new lines", use SonarQube's quality gate or `diff-cover` on the lcov report in CI.

## 4. Bundle budgets (`angular.json`)

Under `projects.<app>.architect.build.configurations.production`. `ng build` fails when a
`maximumError` is exceeded. Angular's defaults are 500 kB / 1 MB for `initial`; the values below are the
stricter example from the Angular docs. Tighten them once you know your real sizes.

```json
{
  "budgets": [
    { "type": "initial", "maximumWarning": "250kB", "maximumError": "500kB" },
    { "type": "anyComponentStyle", "maximumWarning": "2kB", "maximumError": "4kB" },
    { "type": "anyScript", "maximumWarning": "100kB", "maximumError": "200kB" }
  ]
}
```

## 5. Lighthouse CI (`lighthouserc.json` in the frontend folder)

Switched on in CI with `ENABLE_LHCI=true`. Runs Lighthouse 3 times on the production build and asserts
on the median. Lab numbers are a proxy for real-user Core Web Vitals; TBT stands in for INP. Start with
`"warn"` and change to `"error"` once results are stable. Reports are written to disk, not uploaded to a
public server. Replace `dist/your-app/browser` with your build output folder.

```json
{
  "ci": {
    "collect": {
      "staticDistDir": "./dist/your-app/browser",
      "numberOfRuns": 3
    },
    "assert": {
      "assertions": {
        "categories:performance": ["warn", { "minScore": 0.9 }],
        "categories:accessibility": ["warn", { "minScore": 0.9 }],
        "largest-contentful-paint": ["warn", { "maxNumericValue": 2500 }],
        "cumulative-layout-shift": ["warn", { "maxNumericValue": 0.1 }],
        "total-blocking-time": ["warn", { "maxNumericValue": 200 }]
      }
    },
    "upload": {
      "target": "filesystem",
      "outputDir": "./lhci-report"
    }
  }
}
```

## 6. Stryker mutation testing (optional, `stryker.config.json`)

Install with `npm init stryker@latest` (it asks for your test runner). `break` fails the run below
the score; `high`/`low` only colour the report. Start `break` at 60 and raise it over time.

```json
{
  "$schema": "./node_modules/@stryker-mutator/core/schema/stryker-schema.json",
  "testRunner": "karma",
  "mutate": ["src/app/**/*.ts", "!src/app/**/*.spec.ts", "!src/app/**/*.module.ts"],
  "reporters": ["html", "clear-text", "progress"],
  "thresholds": { "high": 80, "low": 60, "break": 60 },
  "incremental": true
}
```

Use `"testRunner": "vitest"` or `"jest"` to match your project.

## 7. Dependency checks

- `npm audit --omit=dev --audit-level=high` fails on known high/critical vulnerabilities in production
  dependencies (CI runs it).
- Before adding a package: `npm view <name> name version time.modified repository.url` - confirm the
  exact name exists, is maintained and points to a real repository. LLMs invent package names, and
  attackers register them ("slopsquatting").
- Commit `package-lock.json` and install in CI with `npm ci`, never `npm install`.

## 8. Copy-paste detection (`.jscpd.json` in the frontend folder, optional)

Catches copied components and services, such as one service per region. CI runs it when the
repository variable `ENABLE_JSCPD` is `true`. Version from memory: check the latest jscpd release.

```json
{
  "threshold": 3,
  "minTokens": 70,
  "reporters": ["console"],
  "ignore": ["**/node_modules/**", "**/dist/**", "**/*.spec.ts", "**/coverage/**"],
  "format": ["typescript", "javascript", "markup", "css", "scss"]
}
```

Run locally with `npx jscpd@4.0.5 src`. A threshold of 3 matches SonarQube's default for duplicated
lines on new code.
